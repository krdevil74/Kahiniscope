# Step 10 — Building and publishing

Two things here need your accounts and cannot be done for you: `eas build`
needs an Expo login, and the Play listing needs the Play Console. Everything
that makes those two short is done.

> **Doing it, rather than reading about it?** `docs/14-play-store-runbook.md`
> is the ordered checklist — what to do first, what waits on what, and how
> long the account verification and the mandatory 14-day closed test take.
> This page is the reference behind it.

### Two things the pre-flight caught

**The owner address was in the app bundle.** The handoff is explicit that
the configured owner address must live in a Cloud Function constant and never reach
the client. It had crept into the emulator sign-in buttons on the sign-in
screen — dead code in a release build, because it is gated on `__DEV__`, but a
string literal survives minification whether or not the code around it can
run. `strings` on the compiled bundle found it. The addresses now come from
`.env`, and the scan is clean:

```
clean: the owner address   clean: TELEGRAM_BOT_TOKEN
clean: WHATSAPP_TOKEN          clean: TEXTBELT_KEY
clean: ESCALATION_RUN_KEY      clean: serviceAccount
```

Worth re-running before any release: export the bundle and `strings | grep` it
for anything that should not be there.

**Three permissions were being requested that the app does not use.**
`expo-dev-client` contributes `SYSTEM_ALERT_WINDOW` — "draw over other apps" —
and the notification tooling contributes the legacy external-storage pair. All
three are now in `blockedPermissions` and are stripped at manifest-merge time.
Asking a production team to grant "draw over other apps" would be a bad first
impression and an awkward question in the data-safety review.

## Building

```bash
npm install -g eas-cli       # the package is eas-cli; the command is eas
cd mobile
eas login
eas init                     # fills EAS_PROJECT_ID
eas build --platform android --profile production
```

`npx eas` does not work — npx resolves a package called `eas`, which is not
the CLI. Either install `eas-cli` globally as above, or run `npx eas-cli@latest`.

Before the first build:

- Put `google-services.json` in `mobile/` (Firebase console → Project settings
  → Android app). It is not in the repository — it is per-project. `app.config.ts`
  wires it up only if present, so prebuild works without it.
- Fill `mobile/.env` from `.env.example` with the Firebase web config and the
  Google web client id.
- Let EAS manage the signing key, and then **back it up**
  (`eas credentials`). Losing it means never being able to update this app
  under this package name again.

`npm run build:preview` produces an APK you can sideload, which is the quickest
way to see the app on a real phone before committing to a store build.

## The listing

Everything written, in `mobile/store/`:

| File | What it is |
| --- | --- |
| `listing.md` | Title, short description (67 chars), full description, category, tags |
| `privacy-policy.md` | Publish this at a public URL; Play rejects a missing one |
| `data-safety.md` | The exact answers for the data-safety form and the content rating |
| `screenshots/` | Filled by `npm run screenshots` |

Graphics are generated by `npm run icons`:

- `assets/store-icon-512.png` — 512×512, no alpha
- `assets/store-feature-graphic-1024x500.png` — 1024×500, no alpha

### Screenshots

`npm run screenshots` captures them over `adb` from a real device or emulator,
prompting for each screen in turn. Seed the demo data first
(`npm run seed:demo`) so the screens have something in them.

They are captured rather than generated on purpose. The handoff suggests
screens from the prototype would do — they would not: the prototype is drawn
in an **iOS device frame**, and a store screenshot that does not match what
installs is the one thing a listing must never do.

### The data-safety answer that is easy to get wrong

The phone number is **shared** — it goes to Meta or to Textbelt in order to
deliver a message. Both of those channels ship switched off, so today nothing
leaves. Declare it as shared anyway: the capability is in the app, and a
declaration that is only true while a setting stays untouched is a declaration
that will be wrong one day.

## The part that takes longest

**If the Play Console account was created after 13 November 2023**, production
access requires a closed test with **at least 12 testers opted in continuously
for 14 days**.

- Recruit **15** to absorb dropouts.
- Real Android devices and real Google accounts only. Emulators and duplicate
  accounts do not count.
- Watch engagement in the Console from day one, not day thirteen.
- Your twelve can be the production team plus friends — and running one real
  episode through the app during those two weeks is the best possible use of
  them.

Organisation accounts and older personal accounts are exempt.

The developer account itself is **25 USD once**, plus identity verification
with a government ID, which takes days. If that has not been started yet, it is
the critical path — start it before the build.

## Order of work from here

1. Open the developer account and start identity verification. *(days)*
2. `eas build --profile preview`, install on a phone, run through both sides.
3. Set the Telegram bot up (`docs/08`) and connect one member end to end.
4. `eas build --profile production`, upload to a closed track.
5. Publish the privacy policy, fill the listing, data safety, content rating.
6. Start the 14-day clock with 15 testers.
7. Run one real episode through the app while the clock runs.
8. Apply for production access; release with a staged rollout.

## What is still untested

installed, no notification has arrived on a device, no Telegram message has

of this app is step 2 of that list, and it should happen before anything is
uploaded anywhere.
